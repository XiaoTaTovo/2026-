# 2026 H：从 TB6612 驱动到整车控制

本文只解释当前 `master/` 的 2026 H B2 固件。证据标签含义：

- `CODE FACT`：源码可直接确认。
- `BUILD FACT`：真实工具链已经生成和链接通过。
- `PHYSICAL INFERENCE`：由电机或差速车物理关系推断，仍需实物验证。
- `UNVERIFIED`：当前没有板级或整车测量证据。

## 1. 结论先行

`CODE FACT`：电机控制只有这一条链：

```text
B2 路线 -> 左右轮 mm/s -> TB6612 目标 RPM -> 编码器实际 RPM
        -> 前馈 + PI -> PWM 百分比 -> 方向脚/PWM/STBY -> 左右电机
```

平台在 [`ti_mspm0_platform.c:261`](../platform/ti_mspm0_platform.c#L261) 构造整车
配置，并在 [`ti_mspm0_platform.c:328`](../platform/ti_mspm0_platform.c#L328) 直接绑定
`TB6612_DriveSetWheelSpeeds()` 与 `TB6612_DriveReadEncoder()`。不存在第二电机后端。

`BUILD FACT`：严格 C11、GCC `-fanalyzer`、SysConfig 1.28 和 CCS 21/TI Arm Clang
5.1.1 已通过；目标工具链为 0 error / 0 warning。
`UNVERIFIED`：左右轮实际方向、编码器符号、速度 PI 和 R500 轨迹尚未在本次实物确认。

## 3. 为什么会这样运行

### 3.1 TB6612 只理解电信号

TB6612 不理解“350 mm/s”。它只认识：方向脚决定电压方向，PWM 占空比决定平均驱动力，
STBY 决定驱动是否总使能。

`CODE FACT`：平台上电先停 PWM、拉低 STBY、清空方向脚；随后
[`TB6612_Init()`](../tb6612.c#L245) 仍保持 0 PWM 和 STBY Low。真正输出在
[`TB6612_SetMotors()`](../tb6612.c#L266)：

```c
set_pwm(0, 0);
DL_GPIO_clearPins(STBY_PORT, STBY_PIN_STBY_PIN);
set_left_direction(leftPercent);
set_right_direction(rightPercent);
DL_GPIO_setPins(STBY_PORT, STBY_PIN_STBY_PIN);
delay_cycles(CPUCLK_FREQ / 1000000U);
set_pwm(leftPercent, rightPercent);
```

普通话解释：先收油并关总开关，再换方向，开总开关，等约 1 us，最后给 PWM。目标为
0 时，PWM、四个方向脚和 STBY 全部清零。

`PHYSICAL INFERENCE`：正速度时某轮实际倒转，先查接线和两个
`TB6612_*_FORWARD_IN1_HIGH`，不要先改 PID。

### 3.2 编码器怎样知道方向

当前只在编码器 A 相边沿进入中断，再读取 B 相判断方向。ISR 在
[`encoder.c:70`](../encoder.c#L70)：

```c
aHigh = DL_GPIO_readPins(ENC_A_PORT, ENC_A_PIN_AL_PIN) != 0U;
bHigh = DL_GPIO_readPins(ENC_B_PORT, ENC_B_PIN_BL_PIN) != 0U;
gEncoderLeftCount += (aHigh != bHigh) ? ENC_LEFT_SIGN : -ENC_LEFT_SIGN;
```

因此 `724 count/rev` 必须用这份固件的计数方式实测，不能直接抄编码器铭牌的 PPR。

### 3.3 从 mm/s 到目标 RPM

[`tb6612.c:44`](../tb6612.c#L44) 使用：

```text
circumference_mm = pi * wheel_diameter_mm
target_rpm = speed_mm_s * 60 / circumference_mm
```

`d=65 mm`、`v=350 mm/s` 时，周长约 `204.20 mm`，目标约 `102.84 rpm`。这是
`CALCULATED` 目标，不是实际轮速证据。

### 3.4 从计数到实际 RPM

每 50 ms 使用 [`tb6612.c:56`](../tb6612.c#L56) 的公式：

```text
measured_rpm = delta_count * 60000 / (counts_per_rev * elapsed_ms)
```

50 ms 内 62 count 对应 `62*60000/(724*50)=102.76 rpm`。随后
[`update_speed_loop()`](../tb6612.c#L164) 把新值与上次结果各取一半，减少数字跳变，代价
是慢一拍。VOFA `I23/I24` 是原始计数差，`I19/I20` 才是滤波后的实际 RPM。

### 3.5 前馈和 PI 各做什么

[`run_speed_pid()`](../tb6612.c#L72) 当前等价于：

```text
error = target_rpm - measured_rpm
feedforward = sign(target) * (6.0 + 0.225 * abs(target_rpm)) percent
P = 0.250 * error percent
I += 0.600 * error * dt_s percent
PWM = clamp(feedforward + P + I, same-direction range, 60 percent)
```

目标 103 rpm 时前馈约 `29.18%`。若实际 90 rpm，误差 13 rpm，P 再给约 `3.25%`。
I 只负责持续偏慢。代码另有 2 rpm 死区、抗积分饱和、零目标/换向清积分，并禁止正
目标被 PI 算成反向制动。

`PHYSICAL INFERENCE`：前馈低会靠 P/I 硬推；前馈高会一开始冲过头。必须同时看目标
RPM、实际 RPM 和 PWM，不能只凭 PWM 曲线判断速度环。

### 3.6 编码器断线或反向反馈为何能先停机

[`TB6612_DriveReadEncoder()`](../tb6612.c#L480) 先运行双轮运动看门狗。某轮目标达到
10 rpm 后，只有与目标方向一致的计数变化才算“这只轮真的在按命令运动”。断线时计数不变；
编码器符号接反或轮子反转时计数方向错误；两种情况连续 600 ms 都会先清速度环并
`TB6612_Stop()`，再向整车层返回失败，最终锁存 `CAR_FAULT_ENCODER_STALE`。

超时判断先于刷新：恰好在第 600 ms 才来的脉冲已经太晚，不能擦除故障。普通话说，软件
不会因为一根线抖了一下，或者轮子朝反方向动了，就误以为电机正常。`UNVERIFIED`：方向与
600 ms 必须用架空轮分别断开左右编码器、反向拨轮验证。

### 3.7 主循环卡死时，为什么还有第二层保护

上面的 600 ms 保护也是软件；如果整个主循环死在某个函数里，它自己也没有机会运行。
因此 SysConfig 另外启用了 4 s 的 MCU WWDT。它像一个独立倒计时器：正常主循环完整跑到
末尾，才在 [`empty_mspm0g3507.c:277`](../empty_mspm0g3507.c#L277) 重启倒计时；卡在
SPI、ADC、I2C、OLED 或控制代码中间时都喂不到，最终由芯片复位。

[`empty_mspm0g3507.c:303`](../empty_mspm0g3507.c#L303) 让 WWDT 在调试器暂停 CPU 时也
暂停，避免单步调试误复位。不要把喂狗放进定时中断，否则即使主循环已经坏掉，中断仍可能
一直喂狗，第二层保护就失去意义。`UNVERIFIED`：4 s 复位必须用专门的故障注入固件上板测量。

### 3.8 ADC 和 IMU 失败时，为什么不会伪装成正常数据

红外 ADC 在 [`ti_mspm0_platform.c:117`](../platform/ti_mspm0_platform.c#L117) 每次先清
旧完成标志，再启动一次转换；成功或超时都会停止转换。初始化在
[`ti_mspm0_platform.c:219`](../platform/ti_mspm0_platform.c#L219) 明确使用单次模式，
所以第一次读取之后不会在后台不停触发 ADC 中断。

IMU 的每个 SPI 字节都通过 [`ti_mspm0_platform.c:32`](../platform/ti_mspm0_platform.c#L32)
返回“成功/失败”和数据两个结果。只要一个字节超时，
[`Icm42688_ReadSample()`](../drivers/icm42688.c#L109) 就把整帧清零且保持无效，不更新时间戳，
并增加 `read_errors`。普通话说，没读到就是没读到，不能再拿 `0xFF` 冒充新姿态。

### 3.9 应用层只看四个动作

[`drive_port.h`](../drivers/drive_port.h) 只暴露 `set_wheel_speeds/read_encoder/stop/service`。
[`CarFirmware_ApplyOutput()`](../firmware.c#L134) 不碰寄存器。因此排错边界是：

- 左右 mm/s 命令错：路线或巡线层。
- mm/s 对但目标 RPM 错：轮径或换算层。
- 目标 RPM 对但实际 RPM 错：编码器、速度环或电机层。
- 实际 RPM 对但轨迹错：机械几何、红外或等效轮距。

PA8/PA9 只是保留输入脚；没有 UART1 电机外设、串口电机协议或后端选择。调试 UART 和
VOFA UART 只负责看数据、发调参命令，不参与电机执行。

### 3.10 固定调度周期

[`firmware.c:289`](../firmware.c#L289) 固定 IMU 5 ms、红外 10 ms、整车控制 20 ms、
停车刷新 100 ms；TB6612 速度内环独立为 50 ms。路线每 20 ms 更新目标，编码器速度
每 50 ms 更新反馈，这是有意分层。

### 3.11 八路红外怎样得到左右误差

[`CarLineEstimator_Update()`](../core/line_estimator.c#L14) 给通道从左到右赋权：

```text
-3500, -2500, -1500, -500, +500, +1500, +2500, +3500
```

归一化黑色接近 1000、白色接近 0。算法减去局部背景后，找连续的明显黑峰并加权平均：
负数表示线在左，正数表示线在右。它还区分无线、窄主线、宽面标志和分裂噪声；普通
巡线只接受窄主线，A 点检测才接受宽面。

### 3.12 几何先给弧线，PID 只小修

B2 路线在 [`h2026_task.c:59`](../app/h2026_task.c#L59) 固定为
`START -> 1500直线 -> R500右半圆 -> 1500直线 -> R500右半圆找A -> STOP`。

[`route_executor.c:274`](../core/route_executor.c#L274) 使用：

```text
left  = v * (1 - curvature * effective_track / 2)
right = v * (1 + curvature * effective_track / 2)
```

代入 `v=300`、右转 `curvature=-1/500`、等效轮距 `160`，得到左 `348 mm/s`、右
`252 mm/s`。右转外侧左轮更快。若命令是 348/252 而实车向左，查轮子映射/方向。

巡线 PID 在 [`route_executor.c:115`](../core/route_executor.c#L115)：

```text
correction = Kp*position + Ki*integral + Kd*derivative
left += correction; right -= correction
```

当前 `Ki=Kd=0`。线在右侧时 correction 为正，左轮加、右轮减，车头向右。弧线修正
上限只有 20 mm/s，避免红外外环盖掉 R500 前馈。若弯道半径错但线误差很小，应调等效
轮距，不调巡线 PID。

### 3.13 丢线与终点

看不到窄线时，[`route_executor.c:260`](../core/route_executor.c#L260) 记录离最后主线多远，
中心速度降到 60 mm/s；距离加 3 mm 容差达到 80 mm 就停车，所以边界约在 77 mm。

末弧宽面标志必须连续两帧，备用判据还要求背景足够白，均匀灰面不能触发；判断在
[`route_executor.c:349`](../core/route_executor.c#L349)。确认后进入终点补偿，并在
[`route_executor.c:323`](../core/route_executor.c#L323) 保持末弧曲率继续走传感器偏置。

## 4. VOFA 证据

`CODE FACT`：PB2/PB3，115200 8N1，FireWater CSV，100 ms，CRLF，无尾随逗号，
固定 48 个数字字段；发送器在 [`vofa_telemetry.c:578`](../vofa_telemetry.c#L578)。

| 字段 | 精确含义 |
| ---: | --- |
| I0 | uptime，ms |
| I1 | `H2026Mode` |
| I2/I3 | route running / finished，0/1 |
| I4/I5 | route index / track phase |
| I6/I7 | segment progress / total odometry，均 x10=0.1 mm |
| I8 | line valid，0/1 |
| I9-I13 | track position/confidence/active count/mask/pattern |
| I14 | line correction x10=0.1 mm/s |
| I15/I16 | 左/右 mm/s 命令 x10；这是目标，不是实测 |
| I17/I18 | 左/右目标 RPM |
| I19/I20 | 左/右实际 RPM |
| I21/I22 | 左/右 PWM，% |
| I23/I24 | 左/右本次编码器计数差 |
| I25/I26 | 速度采样间隔 ms / 更新次数 |
| I27 | yaw x10=0.1 deg |
| I28/I29 | fault bitmask / route exit reason |
| I30 | line gap x10=0.1 mm |
| I31-I34 | marker streak、确认置信度、确认激活数、补偿距离 x10 |
| I35/I36 | result time ms / valid |
| I37/I38 | encoder current valid / drive active |
| I39-I46 | 红外通道 0..7 的归一化值 0..1000 |
| I47 | TX drop count |

速度环最小查看顺序：`I0 -> I17/I18 -> I23/I24 -> I19/I20 -> I21/I22 -> I28/I37/I38`。
巡线顺序：`I39-I46 -> I13 -> I9/I10 -> I14 -> I15/I16 -> I30`。

`CODE FACT`：从 [`VofaTelemetry_BeginWrite()`](../vofa_telemetry.c#L95) 开始，每写一个
字符都先检查剩余空间；一旦超过 512 byte，整帧不入队并增加 drop 计数。严格主机测试还用
内部 writer 直接验证“恰好装满可发送、多 1 字节整帧丢弃且不越界”，并用各字段极值验证
一帧恰好有 47 个逗号，也就是 48 个字段，且总长不超过 512 byte。

`CALCULATED`：常规 10 Hz 的线速上界为 `512*10*10=51.2 kbit/s`，约占
115.2 kbit/s 的 44.4%。状态变化会额外发帧；`I47` 增加表示帧构造空间不足或 TX 环形
缓冲没有空间，二者都要先降低发送频率或检查是否意外扩充字段。

## 5. 只做一个最小实验

目标：只验证“正目标 -> 两轮物理正转 -> 编码器正反馈 -> 急停关闭”，不调参数。

**准备**：架空两轮；电机电源限流并有物理断电开关；红外下放居中黑线；完成白/黑
标定；VOFA 使用本文 V1 字段；一人盯车、一人盯波形。禁止落地。

**步骤**：保持参数不变，按 KEY1 启动，最多运行 2 s；观察轮向和
`I17-I24/I38`；再次按 KEY1 急停。任一轮反向、异响、电流突升或结构松动时立即物理
断电，不等待软件。

**预期**：两轮都朝车辆前进；`I17/I18>0`；首次有效采样后 `I23/I24>0` 且
`I19/I20>0`；`I21/I22` 为正且不超过 60；急停后下一帧内 `I38=0`、
`I21=I22=0`，`I28` 出现急停位。

**通过规则**：方向、反馈符号和停车全部满足才通过，任何一项失败都不允许调 PI 或落地。

**下一分支**：轮向错查 TB6612 方向宏/接线；轮向对但计数负查编码器通道/符号；目标
和 PWM 正常但计数为 0 查供电、A/B 与中断。本实验通过后，下一阶段才单独做左右编码器
断线看门狗试验。
